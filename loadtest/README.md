# Нагрузочные тесты Jitsi

Инструменты автоматического нагрузочного прогона моста Jitsi: синтетические
встречи через реальный протокол streaming-whisper (кадры `participantId|язык` +
PCM 16 кГц), рампа по числу встреч, съём ресурсов, графики. Прогон поднимает
собственный скретч-сервер (отдельная БД в папке запуска) и не трогает рабочий.

## Состав

- `prepare_samples.py` — нарезка речевых сэмплов (WAV 16 кГц моно) из записей;
- `run_loadtest.py` — автоматический прогон: сервер → рампа встреч → статистика
  → остановка сервера → графики;
- `charts.py` — графики по трассе запуска (нужен python с matplotlib; прогон
  находит его сам и запускает отдельным процессом);
- `samples/` — сэмплы речи (в git не хранятся);
- `results/<дата_время>/` — результат каждого запуска.

## Быстрый старт

```bash
.venv/Scripts/python.exe loadtest/prepare_samples.py   # один раз: нарезать сэмплы
.venv/Scripts/python.exe loadtest/run_loadtest.py --meetings 12 --participants 70 --speakers 10
```

Без аргументов `prepare_samples.py` берёт свежие записи из `data/live/*/system.wav`
и пробу monitor-test; свои файлы: `prepare_samples.py путь/к/записи.wav ...`.

## Параметры прогона

| Параметр | По умолчанию | Значение |
|---|---|---|
| `--meetings` | 12 | максимум встреч (по одной на шаг рампы) |
| `--participants` | 70 | участников на встречу (регистрируются тишиной) |
| `--speakers` | 10 | одновременно говорящих на встречу |
| `--step` | 45 | секунд на шаг рампы |
| `--hold` | 150 | секунд держать максимум перед завершением |
| `--sample` | 5 | период съёма статистики, секунды |
| `--rotate` | 60 | секунд между сменами состава говорящих (0 = выкл) |
| `--port` | 8010 | порт скретч-сервера |
| `--base` | — | не поднимать сервер (использовать запущенный на `--port`) |
| `--label` | — | суффикс папки результатов |
| `--keep-data` | — | сохранить записанное аудио (`data/` в папке запуска) |

Говорящие меняются: каждые `--rotate` секунд активный набор замещается свежей
случайной выборкой из всех участников встречи, каждый говорящий получает
случайный сэмпл со случайной позиции — один и тот же клип не крутится синхронно.

## Результаты запуска

`results/<дата_время>/`:

- `samples.jsonl` — трасса: GPU %, VRAM, RSS/CPU сервера, лаг event loop, число
  участников и активных говорящих, отставание текста по встречам, коэффициент
  успевания `rt_factor` (1.0 = не отстаём), предупреждения;
- `chart_timeline.png`, `chart_scale.png` — графики (раунды декодера, GPU и
  успевание, задержки, ресурсы; устойчивость по числу встреч);
- `server.log` — лог сервера: «декодер не успевает» и «очередь переполнена» —
  маркеры перегрузки;
- `summary.json` — итог: стена (если упёрлись в ресурс), статусы задач, ротации.

## Наблюдаемые пределы

Один декодер (нить + GPU) обслуживает ~25–30 одновременных говорящих потоков
(окно 3 с, ~0.11 с на строку батча). 10-говорящие встречи: комфортно 2, предел 3;
дальше отставание растёт линейно, а жёсткие стены по VRAM/RAM/дискам не
достигаются — деградация идёт по пропускной способности декодера.
Перегрузочные гварды моста: `MEETSCRIBE_BRIDGE_DRAIN_MAX_SEC` (4 с аудио на
участника за раунд) и `MEETSCRIBE_BRIDGE_PENDING_MAX_SEC` (120 с очереди на
участника; глубже — дроп старейших кадров с предупреждением; запись не страдает).
