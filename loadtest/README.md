# Нагрузочные прогоны Jitsi

Инструменты автоматического нагрузочного теста системы транскрибации:
синтетические встречи, говорящие по реальному протоколу streaming-whisper
(кадры `participantId|язык` + PCM 16 кГц), рампа по числу встреч, ротация
говорящих, съём ресурсов и графики. Раннер по умолчанию поднимает собственный
скретч-сервер (отдельная БД в папке запуска) и не трогает рабочий;
`--target` позволяет нагрузить любой готовый сервер, в том числе прод.

---

## Состав

| Файл | Назначение |
|---|---|
| `prepare_samples.py` | Нарезка речевых сэмплов (WAV 16 кГц моно) из живых записей; чанки ставятся только на громкие участки. |
| `run_loadtest.py` | Прогон: сервер → рампа встреч → статистика → предохранители → итоги и графики. |
| `charts.py` | Графики по трассе (нужен Python с matplotlib; раннер находит его сам). |
| `check_charts_asr.py` | Рендер трасс без серверной GPU (у контейнера сервера нет nvidia-smi) — проверка панелей. |
| `samples/` | Сэмплы речи (в git не хранятся). |
| `results/<дата_время>/` | Результат каждого прогона. |

## Быстрый старт

```bash
python loadtest/prepare_samples.py                        # один раз: нарезать сэмплы
python loadtest/run_loadtest.py --meetings 12 --participants 70 --speakers 10
```

`prepare_samples.py` без аргументов берёт пробу монитора, 6 свежих live-записей
(`system.wav` + `mic.wav`) и крупнейшую дорожку каждой из 8 свежих jitsi-задач;
каждый чанк — на самом громком окне рядом с якорем (тишина-заполнитель jitsi не
попадает в сэмплы), молчащие и слишком короткие источники пропускаются,
устаревшие сэмплы подчищаются. Свои источники (файлы/папки) — аргументами
(`prepare_samples.py путь/к/записи.wav папка/ ...`): не-WAV и не-16-кГц-моно
перегоняются через ffmpeg (`MEETSCRIBE_FFMPEG` из `.env`, иначе PATH).
Число сэмплов: `--count N` (целевое общее) или `--per-source` (по умолчанию 3).

## Параметры прогона

| Параметр | По умолчанию | Значение |
|---|---|---|
| `--meetings` | 12 | максимум встреч (по одной на шаг рампы) |
| `--participants` | 70 | участников на встречу (регистрируются тишиной) |
| `--speakers` | 10 | одновременно говорящих на встречу |
| `--step` | 45 | секунд на шаг рампы |
| `--hold` | 150 | секунд держать максимум перед завершением |
| `--sample` | 5 | период съёма статистики, секунды |
| `--rotate` | 60 | секунд между сменами состава говорящих (0 — выкл.) |
| `--rss-wall` | 8000 | стена по RSS сервера, МБ (0 — без стены) |
| `--port` | 8010 | порт скретч-сервера |
| `--base` | — | не поднимать сервер (использовать запущенный на `--port`) |
| `--target` | — | адрес целевого сервера как у jigasi: `https://127.0.0.1`, `http://host:8000`… |
| `--label` | — | суффикс папки результатов |
| `--keep-jobs` | — | не удалять синтетические задачи с внешнего сервера |
| `--keep-data` | — | сохранить записанное аудио (`data/` в папке запуска) |

Каждые `--rotate` секунд активный набор говорящих замещается свежей случайной
выборкой из всех участников встречи, каждый говорящий получает случайный сэмпл
со случайной позиции — один и тот же клип не крутится синхронно.

## Прогон против готового сервера (включая прод)

`--target` — адрес целевого сервера Стенографа (тот же, что jigasi пишет в
`JIGASI_TRANSCRIBER_WHISPER_URL`, без хвоста `/ws`):

```bash
python loadtest/run_loadtest.py --target https://127.0.0.1 \
    --meetings 6 --speakers 10 --rotate 60
```

- `http(s)://host[:port]` или `ws(s)://host[:port]` — API- и ws-адреса выводятся
  автоматически; самоподписанный TLS принимается.
- Чужой сервер прогон **никогда не останавливает** — остановка только у скретча,
  который он поднял сам.
- Каждой синтетической встрече принудительно включается распознавание
  (`POST /api/jitsi/transcribe`) — измеряется и режим «только запись».
- После прогона синтетические задачи `load-m*` этого запуска с целевого сервера
  удаляются (встречи и их авто-улучшения; у встреч, доигрывающих финализацию,
  дети сперва отменяются, чтобы не жечь GPU на тестовом аудио). При цели на этой
  машине (`127.0.0.1`/`localhost`) вместе с задачами убираются медиа-папки
  `data/jitsi/<id>` и аудио-кэши. `--keep-jobs` отключает уборку.
- Прод деградирует ровно так же, как скретч (в этом и смысл замера): файловые
  задачи на время прогона ждут гейт эфира, финализация встреч может занять
  дополнительные минуты.
- Ctrl+C — аккуратная остановка: встречи закрываются, задачи и медиа убираются,
  итоги и графики строятся всё равно; повторный Ctrl+C — немедленный выход.

## Результаты запуска

`results/<дата_время>/`:

| Файл | Содержимое |
|---|---|
| `samples.jsonl` | Трасса по тикам: число встреч/участников/активных говорящих, лаг event loop, health, отставание текста по встречам (`delays_map`, `delay_avg/max`), коммит-рейт и коэффициент успевания `rt_factor` (1.0 = не отстаём), ресурсы сервера; в remote-режиме — и цифры внешнего ASR-сервиса (`asr_gpu_pct`, `asr_cpu_pct`, `asr_vram_*`, `asr_rss_mb`, `asr_models`). |
| `chart_timeline.png`, `chart_scale.png` | Графики: раунды декодера, GPU/VRAM (панель GPU переключается на внешний сервис, если у сервера своей nvidia-smi нет), успевание, задержки, ресурсы (сервер — сплошными, внешний сервис — пунктиром), устойчивость по числу встреч. |
| `server.log` | Лог сервера: маркеры перегрузки («декодер не успевает», «очередь переполнена»). |
| `summary.json` | Итог: стены/аборт, статусы задач, ротации, время. |

## Проведённые прогоны и результаты (11.10.2026)

Стенд: Windows + Docker Desktop (WSL2), один GPU; конфигурация — docker-стек
(сервер + внешний ASR-сервис). Профиль «ultra»: до 20 встреч, по 80 участников,
15 говорящих с ротацией каждые 20 с.

Итоги трёх полных прогонов (18 встреч на пике ≈ 1440 одновременных подключений,
~270 говорящих потоков):

- **Сервер** держал рампу целиком: лаг event loop ≤ 0.47 с на пике, без
  перезапусков; приём и сохранение аудио всех потоков — без потерь.
- **Записи** всех 18 встреч транскрибированы (15–1074 сегментов на встречу,
  ≈4.6 тыс. сегментов суммарно), авто-улучшения (moss, до 80 дорожек) досчитаны.
- **ASR-сервис** — узкое место: 98–100 % GPU, до ~460 % CPU.
- **Живые субтитры** на пике отстают: `delay_max` ~280–286 с к концу рампы,
  `rt_factor` ≤ 0.05 — GPU не успевает за реальным временем на этой
  конфигурации. Деградация по пропускной способности, не отказ: очереди
  принимаются, сервер жив, обслуживание файлов продолжается после пика.
- **Смоук 1 × 10 говорящих**: `delay_max` ~10 с, GPU 98 %, CPU ~460 %,
  лаг сервера 16 мс.
- Прогоны останавливает предохранитель раннера (три промаха health подряд в
  окне шторма переподключений ~1500 TCP; это известное поведение docker-прокси —
  приложение при этом отвечает, рестартов нет).

Вывод по ёмкости: one-GPU конфигурация уверенно держит единично-несколько
встреч в realtime; масштаб числа встреч упирается в GPU-пропускную способность
(см. графики `chart_*`) и масштабируется ускорением, а не сервером.

## Предохранители и кэпы

Стены прогона: три промаха health подряд, свободный VRAM ≤ 800 МБ, лаг event
loop ≥ 5 с, RSS сервера ≥ `--rss-wall` (по умолчанию 8 ГБ). При стене рампа
останавливается, встречи закрываются, итог фиксируется.

Перегрузочные гварды моста (в проде работают всегда):

| Параметр | Смысл |
|---|---|
| `MEETSCRIBE_BRIDGE_DRAIN_MAX_SEC` | сколько секунд аудио на участника дренируется за раунд (по умолчанию 4 с) |
| `MEETSCRIBE_BRIDGE_PENDING_MAX_SEC` | порог очереди на участника (30 с; глубже — дроп старейших кадров с предупреждением, запись не страдает) |
| `MEETSCRIBE_BRIDGE_TOTAL_PENDING_MAX_SEC` | порог очереди на весь сервер (20 мин аудио; надзор раз в секунду дропает старейшее из самых толстых очередей) |
| `MEETSCRIBE_BRIDGE_FINALIZE_CONCURRENCY` | сколько встреч одновременно дренят бэклог при финализации (по умолчанию 2) |

## Наблюдаемые пределы

- Пропускная способность определяется GPU: один декодер обслуживает порядка
  ~25–30 одновременных говорящих потоков (окно 3 с, ~0.11 с инференса на строку
  батча). 10-говорящие встречи: комфортно 2, предел 3 — дальше отставание растёт
  линейно; жёсткие стены по VRAM/RAM не достигаются — деградация идёт по
  пропускной способности.
- При полной рампе (десятки потоков) финализация закрытых встреч дренирует
  накопленные буферы минутами; на это время внешние health-пробы могут давать
  сбои, но сервер остаётся жив, а аудио на диске не страдает.
- `--keep-jobs` позволяет потом посмотреть задачи в UI; без него раннер сам
  удаляет свои `load-m*` с сервера.
