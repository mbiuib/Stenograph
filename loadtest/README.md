# Нагрузочные тесты Jitsi

Инструменты автоматического нагрузочного прогона моста Jitsi: синтетические
встречи через реальный протокол streaming-whisper (кадры `participantId|язык` +
PCM 16 кГц), рампа по числу встреч, съём ресурсов, графики. По умолчанию прогон
поднимает собственный скретч-сервер (отдельная БД в папке запуска) и не трогает
рабочий; `--target` позволяет нагрузить любой готовый сервер, включая прод
(см. «Прогон против готового сервера»).

## Состав

- `prepare_samples.py` — нарезка речевых сэмплов (WAV 16 кГц моно): проба
  монитора, свежие live-записи (system+mic), дорожки последних jitsi-задач;
  чанки ставятся только на громкие участки;
- `run_loadtest.py` — автоматический прогон: сервер → рампа встреч → статистика
  → остановка сервера → графики;
- `charts.py` — графики по трассе запуска (нужен python с matplotlib; прогон
  находит его сам и запускает отдельным процессом);
- `samples/` — сэмплы речи (в git не хранятся);
- `results/<дата_время>/` — результат каждого запуска.

## Быстрый старт

```bash
.venv/Scripts/python.exe loadtest/prepare_samples.py   # один раз: нарезать сэмплы
.venv/Scripts/python.exe loadtest/run_loadtest.py --meetings 12 --participants 70 --speakers 10
```

Без аргументов `prepare_samples.py` берёт пробу монитора, 6 свежих live-записей
(`system.wav` + `mic.wav`) и крупнейшую дорожку каждой из 8 свежих jitsi-задач,
ставит каждый чанк на самое громкое окно рядом с якорем (тишина-заполнитель
дорожек jitsi не попадает в сэмплы), молчащие и слишком короткие источники
пропускает, устаревшие сэмплы подчищает. Свои источники (файлы или папки):
`prepare_samples.py путь/к/записи.wav папка/ ...` — формат любой: не-WAV и
не-16-кГц-моно источники перегоняются через ffmpeg (`MEETSCRIBE_FFMPEG` из
`.env`, иначе PATH).

## Параметры прогона

| Параметр | По умолчанию | Значение |
|---|---|---|
| `--meetings` | 12 | максимум встреч (по одной на шаг рампы) |
| `--participants` | 70 | участников на встречу (регистрируются тишиной) |
| `--speakers` | 10 | одновременно говорящих на встречу |
| `--step` | 45 | секунд на шаг рампы |
| `--hold` | 150 | секунд держать максимум перед завершением |
| `--sample` | 5 | период съёма статистики, секунды |
| `--rotate` | 60 | секунд между сменами состава говорящих (0 = выкл) |
| `--port` | 8010 | порт скретч-сервера |
| `--base` | — | не поднимать сервер (использовать запущенный на `--port`) |
| `--target` | — | адрес целевого сервера как у jigasi: `https://127.0.0.1`, `http://host:8000`… |
| `--label` | — | суффикс папки результатов |
| `--keep-jobs` | — | не удалять синтетические задачи с внешнего сервера |
| `--keep-data` | — | сохранить записанное аудио (`data/` в папке запуска) |

Говорящие меняются: каждые `--rotate` секунд активный набор замещается свежей
случайной выборкой из всех участников встречи, каждый говорящий получает
случайный сэмпл со случайной позиции — один и тот же клип не крутится синхронно.

## Прогон против готового сервера (в том числе прода)

`--target` — адрес целевого сервера «Стенограф», тот же, что jigasi пишет в
`JIGASI_TRANSCRIBER_WHISPER_URL` (хвост `/ws` не нужен):

```bash
.venv/Scripts/python.exe loadtest/run_loadtest.py --target https://127.0.0.1 \
    --meetings 6 --speakers 10 --rotate 60
```

- `http(s)://host[:port]` или `ws(s)://host[:port]` — API- и ws-адреса выводятся
  автоматически; самоподписанный TLS принимается (проверка сертификата выключена).
- Чужой сервер прогон **никогда не останавливает** — остановка только у скретча,
  который он поднял сам.
- Каждой синтетической встрече принудительно включается распознавание
  (`POST /api/jitsi/transcribe`), поэтому режим «только запись» тоже измеряется.
- После прогона синтетические задачи `load-m*` этого запуска удаляются с
  целевого сервера — и встречи, и их авто-улучшения (если сервер чейнит их
  при закрытии встречи: дети сначала отменяются, чтобы не жечь GPU на тестовом
  аудио; встречи, ещё доигрывающие финализацию, не трогаются). При цели на
  этой машине (`127.0.0.1`/`localhost`) вместе с задачами убираются их
  медиа-папки `data/jitsi/<id>` и аудио-кэши — сервер при удалении задачи
  файлы не трогает. `--keep-jobs` отключает уборку.
- Прод деградирует ровно так же, как скретч (в этом и смысл замера): файловые
  задачи на время прогона ждут гейт эфира, а после остановки встреч их
  финализация (досчёт бэклога) может занять ещё несколько минут.
- Ctrl+C — аккуратная остановка: встречи закрываются, задачи и медиа на цели
  убираются, итоги и графики строятся всё равно; повторный Ctrl+C — немедленный
  выход.

## Результаты запуска

`results/<дата_время>/`:

- `samples.jsonl` — трасса: GPU %, VRAM, RSS/CPU сервера, лаг event loop, число
  участников и активных говорящих, отставание текста по встречам, коэффициент
  успевания `rt_factor` (1.0 = не отстаём), предупреждения;
- `chart_timeline.png`, `chart_scale.png` — графики (раунды декодера, загрузка
  и видеопамять GPU, успевание, задержки, ресурсы; устойчивость по числу
  встреч);
- `server.log` — лог сервера: «декодер не успевает» и «очередь переполнена» —
  маркеры перегрузки;
- `summary.json` — итог: стена (если упёрлись в ресурс), статусы задач, ротации.

## Наблюдаемые пределы

Один декодер (нить + GPU) обслуживает ~25–30 одновременных говорящих потоков
(окно 3 с, ~0.11 с на строку батча). 10-говорящие встречи: комфортно 2, предел 3;
дальше отставание растёт линейно, а жёсткие стены по VRAM/RAM/дискам не
достигаются — деградация идёт по пропускной способности декодера.
Перегрузочные гварды моста: `MEETSCRIBE_BRIDGE_DRAIN_MAX_SEC` (4 с аудио на
участника за раунд) и `MEETSCRIBE_BRIDGE_PENDING_MAX_SEC` (120 с очереди на
участника; глубже — дроп старейших кадров с предупреждением; запись не страдает).
