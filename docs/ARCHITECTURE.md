# Архитектура «Стенографа»

Документ фиксирует слои, потоки и принятые решения. Обновляется по мере
движения по milestone-плану.

## Принципы

- **Ядро не знает о конкретных моделях.** ASR- и диаризация-движки подключаются
  за протоколами (`engines/base.py`) через реестр (`engines/__init__.py`).
  Новый бэкенд — новый модуль, ядро не меняется.
- **Один конвейер — три источника.** Файл, live-захват (микрофон + системный
  звук) и Jitsi-мост (Jigasi) сходятся в одни и те же события и хранилище.
- **Единый контракт событий** для SSE, будущего WebSocket и CLI (`events.py`).
- **Локальность.** ASR и диаризация выполняются на своей машине. Наружу уходит
  только текст после явного действия пользователя — в LLM-постобработку
  (OpenAI-совместимый API: LM Studio, Ollama, vLLM или облако по выбору).

## Слои

```
domain/     модели и ошибки; ни от чего не зависят
engines/    протоколы + реализации ASR/диаризации + реестр
media.py    ffmpeg: probe, извлечение 16 кГц моно
storage.py  SQLite-репозиторий задач (WAL, версия схемы)
events.py   шина событий (fan-out, потокобезопасная)
pipeline.py стадии файловой задачи + переходы состояний
service.py  очередь (FIFO), один GPU-воркер, отмена
api/        FastAPI: тонкие роутеры, SSE
cli.py      тот же конвейер из командной строки
```

Зависимости направлены вниз: `api/cli → service → pipeline → engines → domain`.
Обратных зависимостей нет.

## Поток файловой задачи (M0, работает)

```
upload (API) или `stenograph transcribe` (CLI)
  → service.submit_file()  [queued]
  → воркер (один поток)
      probe (ffprobe)                    1–2 %
      extract 16 кГц моно (ffmpeg)       2–5 %
      ASR-движок, сегменты стримятся     5–99 %
        → события segment/progress; ре-сплит длинных сегментов
      persist (SQLite) + done            100 %
```

Отмена — кооперативная: `threading.Event` → движок проверяет между сегментами
и бросает `JobCancelled`.

## Планируемые источники

### Live-захват (SfB и любые приложения без серверной интеграции)
Две дорожки: системный звук (WASAPI loopback) → «Они», микрофон → «Вы».
Захват серверный (приложение локально), браузерный `getDisplayMedia` — опция
для удалённого доступа. Ядро: VAD + скользящее окно + согласование гипотез
(LocalAgreement) на faster-whisper turbo; задержка ~1.5–3 с. Аудио сессии
сохраняется для последующего полного оффлайн-прогона.

### Jitsi-мост (Jigasi)
Jitsi штатно умеет отдавать аудио конференции внешнему сервису: Jigasi
подключается к нашему WebSocket и шлёт бинарные пакеты — заголовок 60 байт
`participantId|язык` + PCM 16 кГц. Мы отвечаем JSON:
`{"type": "partial"|"final", "participant_id", "text", "variance"}`.
Это протокол jitsi/skynet streaming-whisper (Apache-2.0).

Что получаем: субтитры прямо в интерфейсе Jitsi, транскрипт с бесплатной
атрибуцией по участникам (id говорящего приходит в заголовке — академическая
диаризация для Jitsi не нужна) и историю у нас.

## Движки (план состава)

| Роль | Дефолт | Альтернативы |
|---|---|---|
| ASR файлов (оффлайн) | MOSS-Transcribe-Diarize | faster-whisper large-v3 |
| ASR live | faster-whisper large-v3-turbo | GigaAM-v3-rnnt, T-one |
| Диаризация (whisper-путь) | pyannote 3.1 | DiariZen |
| Текст: протокол/саммари | LLM из LM Studio по API | любой OpenAI-совместимый |

MOSS делает ASR+диаризацию за проход: разделение спикеров точнее, чем у
whisper+pyannote, плата — скорость, поэтому live остаётся за whisper-turbo.
Длинные файлы режутся на чанки по 300 с с перехлёстом 2 с; дубликаты на
границах снимаются по времени и схожести текста (Jaccard). Метки спикеров
локальны для чанка (S01→SPEAKER_00); сквозная идентичность между чанками —
плановая доработка. Диаризация-протокол для whisper-пути (pyannote/DiariZen)
пока не подключён.

## Ключевые решения

1. ASR и диаризация — всегда локально в процессе приложения: у LM Studio нет
   STT-эндпойнта, а генеративные LLM не годятся для аудио.
2. Текстовые LLM — внешний сервис: снимает конкуренцию за VRAM, версии
   transformers и обновления моделей.
3. Live-спикеры берутся из источника (две дорожки / participant id в Jitsi),
   а не акустической диаризацией на лету.
4. Один GPU-воркер для файловой очереди + отдельная очередь live-декодера:
   live-сессии не конкурируют за GPU, декодер обслуживает их по кругу
   ограниченными ходами, догоняя отстающих по мере возможностей.

## Live-режим (M3)

Захват: браузерный (`getUserMedia` микрофон + `getDisplayMedia` звук системы,
16 кГц моно, 100-мс кадры в WS `/ws/live`) и серверный (PyAudioWPatch/WASAPI —
loopback устройства вывода по умолчанию «Они» + микрофон «Вы», чанки 0.2 с).
`soundcard` отвергнут: зависает при открытии loopback некоторых Bluetooth-устройств.

Несколько сессий идут одновременно: браузерных — сколько угодно, серверный
захват — не более одной сессии (устройства машины общие). Транскрибация
сериализуется через одну очередь: декодер-воркер обслуживает сессии ходами
(FIFO-ротация, до `live_turn_ticks` инференсов и `live_turn_sec` секунд GPU на
ход), поэтому whisper не запускает N потоков разом, а аудио каждой записи
догоняет, когда до неё доходит очередь. Очередь и задержка отдаются в
`GET /api/live/status` (`sessions[].queue_position` / `lag_sec`).

Клиент владеет захватом в модульном сторе (`frontend/src/live/session.ts`), а не
в компоненте страницы: переход по вкладкам сервиса запись не прерывает, страница
Live лишь подписывается на состояние. Остановить сессию можно откуда угодно
(`/api/live/stop` c `job_id`, кнопка на странице задачи) — сервер после
финализации сам закрывает upload-сокет, и страница записи показывает итог.

Декодирование: `StreamTracker` на каждый трек — окно нестабильного аудио, инференс
раз в `live_step_sec` (0.8 с) на окне целиком, коммит слов, согласованных в двух
последовательных гипотезах (LocalAgreement-2); тишина отсекается по RMS;
закоммиченное аудио выбрасывается из окна, переросшее окно принудительно
коммитится; модель whisper-turbo, greedy (beam 1). Спикеры — по источникам.

Сессия — это job (`kind="live"`): тот же SSE-контракт (+ события `partial` и
`level`), страница задачи показывает финальный транскрипт с метками «Они»/«Вы».
Аудио дорожек пишется в `data/live/<id>/<track>.wav` для офлайн-обработки.

Улучшение записи (reprocess): после остановки сессии сервис создаёт дочернюю
задачу `kind="reprocess"` — каждая дорожка перетранскрибируется с нуля движком
по умолчанию (moss), сегменты сливаются в общий таймлайн: микрофон помечается
«Вы», системная дорожка сохраняет диаризованные метки движка. Задачи связаны
через `meta.parent` / `meta.reprocess_job`; автозапуск управляется
`live_auto_reprocess`. Прогресс идёт дорожка за дорожкой по общей очереди
одного воркера.

## Веб-интерфейс (M2)

React + TypeScript + Vite + Tailwind, собирается в `frontend/dist` и
раздаётся тем же FastAPI (SPA-fallback; API-роуты имеют приоритет, неизвестные
`/api/*` — 404). В dev-режиме `npm run dev` проксирует `/api` на :8000.

Данные: дашборд — `/api/stats` + `/api/queue` (поллинг ~2 c, ETA считается на
клиенте от прогресса и времени старта), страница задачи —
`/api/jobs/{id}/events` (SSE: snapshot → status/progress/segment →
segments_replaced → done/error). Контракт событий — тот же, что у CLI.
